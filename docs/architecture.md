# Architecture

Read [`design.md`](design.md) first for the product model and the invariants. This document maps that design to crate boundaries and the deployment topology; where a piece is committed direction rather than current, it says so.

The gateway executable owns model-account lifecycle without starting its daemon runtime or loading configuration:

```text
dekopond auth chatgpt
  -> fixed OpenAI device-auth host
  -> isolated Dekopon credential file
```

## Current workspace ownership

The workspace holds 23 crates and ships two binaries, `dekopond` and `dekopon-brokerd`.

The gateway owns chat and model credentials, bounded agent sessions, and proposals — never a provider credential or broker authority. The broker alone authorizes provider effects, resolves destination-bound credentials (the legacy bindings [will be replaced by DRNs](design.md#legacy-credential-bindings)) or separately authorized public DRNs, and records every decision as an audit log record inside the caller's trace; losing the log exporter loses audit ([non-goals](design.md#non-goals)).

Crate boundaries:

- `dekopon-core`: validated identifiers and dependency-light domain enums — the canonical public `SecretDrn`, the typed inert `SecretUseProposal`, and the `SkillId` grammar a mounted skill's directory and front matter must share. It also owns the two filesystem facts separate processes must not disagree about: what makes a local file trusted input, and which permission tier — private, or merely not world-writable — a file is held to.
- `dekopon-capability`: capability metadata and the proposal and authorization invocation states.
- `dekopon-protocol`: strict `dekopon.dev/v1alpha1` resources and list responses.
- `dekopon-config`: discovery, parsing, duplicate detection, reference validation, and the bounded in-memory `Skill` loader for `SKILL.md` directories. The catalog runs that loader at load time, so a session never touches the filesystem for a skill.
- `dekopon-provider-sdk`: typed Rust guest trait, manifest and response wire types, and adapters for its default or a caller-generated provider world. Its optional non-default `host` feature holds the shared manifest rules, conflict reports, store bounds, and engine construction that the broker host, the testkit, and external embeddings share; a guest build never enables it.
- `dekopon-provider-http`: guest-only Rust facade over the published buffered HTTP interface.
- `dekopon-provider-clock`: guest-only Rust facade over the published `dekopon:clock` wall clock interface, which the broker host answers during an authorized invocation only.
- `dekopon-provider-storage`: feature-gated guest-only JSONL and durable-files bindings, with no namespace, path, or authority API.
- `dekopon-http-host`: the statically linked native buffered HTTP engine. It consumes HTTP constraints beneath independent ceilings, equality-checks authorization-bound DRN credentials, enforces secret-specific authority, method, path, query, and injection scope, renders Basic and Bearer, checks and pins DNS results, disables redirects and ambient proxies, emits sanitized metadata, and refuses a response that echoes the credential.
- `dekopon-storage-host`: the privileged namespace, key, layout, quota, lease, direct-write, JSONL, and durable-file engine. It links no Wasmtime and sits outside `dekopond`'s dependency tree; a gateway integration test may take it as a dev-dependency. CI gates the opposite direction too, keeping orchestration crates out of `dekopon-brokerd`; `dekopon-model` is allowed for its shared `chatgpt::CredentialFile` refresh implementation.
- `dekopon-broker-host`: the privileged asynchronous Wasmtime component host adapting project-owned HTTP, storage, and wall clock imports. It accepts only an authorized invocation and exact single-use storage grants, and runs compiled components on a shared async engine behind fresh fuel- and memory-bounded stores with wall-clock cancellation and typed WIT adaptation. Only an invocation's store answers the clock; a description or command run that reads it traps.
- `dekopon-policy`: the bounded, deterministic Cedar adapter — a schema generated from the deployment's declared principals, providers, and capabilities; strict startup validation; entity literals proved against that world; deny on any evaluation error; the determining policy identifiers and a policy-set digest per decision. Only `dekopon-broker` and `dekopon-brokerd` consume it. It holds no execution authority: constraint sets stay outside the policy language, so a policy edit can broaden who may act and can never widen a timeout, a destination, or a credential binding.
- `dekopon-broker`: deny-by-default authorization over owner-authored constraint sets, trusted context binding, single-use authorization, public evidence, and audit coordination around the component host. Constructing an `AuthenticatedContext` does not authenticate it.
- `dekopon-broker-protocol`: strict versioned messages and the unprivileged Unix client, with one-request-per-connection framing under hard byte and deadline ceilings and a client that verifies protected socket metadata and the server peer UID. The invocation payload carries a proposal and a result and omits principal, actor, policy, constraints, credentials, and authorization; the crate depends on no broker host and no native HTTP.
- `dekopon-brokerd`: the Unix-only privileged process — strict owner-controlled configuration, a separate owner-only Cedar policy file and per-capability constraint sets, private socket lifecycle, peer-UID context mapping, credential resolution, an owner-only public-DRN-to-private-source map with bounded per-invocation adapters, bounded concurrency and shutdown, provider execution, audit as log records, and a `provider` command tree (sync, list, verify). The provider manager keeps operator-authored exact OCI references, generated immutable resolutions, and installed content-addressed bytes distinct; startup constructs no registry client and passes expected lock identities into the component host's exact-read compile boundary.
- `dekopon-model`: the bounded chat-model contract — OpenAI-compatible transport and isolated ChatGPT/Codex authentication and Responses client. Its `chatgpt::CredentialFile` owns the refresh sequence shared by the gateway and the broker's `chatgptSubscription` credential. It holds no image client, provider, broker, or policy code: producing an image is a broker-authorized provider effect.
- `dekopon-telemetry`: OTLP exporter settings and the subscriber every exporting executable installs. Ingest credentials are read from the standard `OTEL_EXPORTER_OTLP_HEADERS` environment variable, so no configuration file, command line, or span attribute holds one.
- `dekopon-shell`: the sandboxed bash-flavored script parser and tree-walking interpreter whose command words dispatch to capabilities through one abstract seam. It links no Wasmtime, broker, HTTP, or filesystem code and owns its own step, recursion, output, deadline, and capability-call bounds. It emits a `tracing` span per command word and links no exporter: the embedding binary's subscriber decides where those go, the way `curl` there assembles a request for a capability rather than opening a socket.
- `dekopon-process`: the unprivileged one-run/one-node Tokio lifecycle seam behind one async `Process` trait. It records run and node identity as span fields, preserves either the typed operation result or a Tokio `JoinError`, and transfers the node to a self-contained supervisor before its first await; while the owning runtime lives, that supervisor joins, records, and delivers the node to a required abandonment observer even when the outer `execute` caller is dropped. Its only cancellation is the cooperative `CancelHandle`/`CancelSignal` pair: the supervisor aborts a cancellable node's task at its next await and joins it before reporting. It owns no scopes, ports, deadlines, graph scheduling, provider, Wasmtime, transport, policy, credential, retry, or persistence code.
- `dekopon-agent`: the shared agent session layer — the bounded scripting prompt loop with an optional cooperative cancellation probe; optional bounded meta tools (asset fetch, `inspect_agent_config`, `read_skill` over mounted skills, `suggest_improvement`), each offered only when the embedder supplies or enables it; a session-wide capability budget spent on fresh interpreters; composite direct-then-broker capability dispatch; and a synchronous broker-leg facade over the protocol client whose command-word runs are cancellable `dekopon-process` nodes. That leg strips the reserved `attachments` result key into a bounded request-local slot and expands `chat-asset:<N>` input markers through an embedder-supplied reader for listed capabilities. Attachment bytes bypass the model transcript and conversation history. Its typed configuration view has no credential, identity, endpoint, path, constraint, or raw-policy field, and it lists mounted skills by name, description, and resource path, never their text. It holds no authority, and of the broker crates it depends only on the client half of the protocol. `dekopond` and out-of-tree clients consume this layer.
- `dekopond`: the Unix-only unprivileged chat gateway and agent daemon — strict owner-controlled configuration; Slack Socket Mode, Discord Gateway, Telegram long-poll, text-only Meta WhatsApp Cloud API, and local development transports; first-match routing to catalog agents; route-scoped opt-in `providerAttachments` delivery and `chatAssetInputs` expansion; typed text and attachment replies; authorization-fed bounded Slack Agent thread ownership; request-scoped optional no-reply decisions; opt-in transport-native in-flight activity after authorization; Slack Agent Stop handling through cooperative prompt and tool cancellation that also abandons an in-flight broker command run; admission-bounded sessions on the shared `dekopon-agent` loop; credential-free self-inspection built from gateway-owned prompt metadata plus the broker's fresh effective grant; the agent's catalog skills mounted on every session of its route with per-route opt-in `improvementSuggestions`; and attested on-behalf-of proposals to the broker. The WhatsApp listener is plain HTTP behind operator-owned TLS termination, authenticates exact raw webhook bytes before parsing, and answers text only through the pinned Graph messages endpoint without retrying an outcome-unknown send. It holds chat and model credentials, never a provider credential, and a CI dependency gate keeps every privileged broker crate out of its tree. Attachment delivery, activity, and continuation targets come only from owner configuration and authenticated transport envelopes; filenames, endpoints, credentials, status content, and the fixed Slack reaction fallback are gateway-owned, and the model can select neither a thread nor a sender.
- `dekopon-provider-sdk-testkit`: the in-process fake broker for provider test suites. It mints its own authorization through `AuthorizationGate`, skipping Cedar and the constraint catalog, and runs the real component against a real `StorageHost` over a temporary root. Out-of-tree provider repositories consume it; it holds no authority of its own, and nothing in the daemon path depends on it.
- `dekopon-test-support`: unpublished shared test scaffolding (`publish = false`), reached only as a path `[dev-dependencies]` entry so it never enters a published manifest or the CI dependency-tree gates; see [`development.md`](development.md#repository-map).

## Deployment boundary

The deployment is two separate running processes; model auth is a separate gateway command:

```text
dekopond
    chat transports, routing, model interaction, bounded sessions,
    bounded per-conversation history; optional post-acceptance durable recording
    (durable retrieval is explicit and on demand, never automatic prompt replay)

dekopon-brokerd
    authorization, credentials, provider execution, external effects
```

`dekopond` is unprivileged and holds no broker authority. `dekopon-brokerd` is a separate process for local Unix deployment; a pod boundary needs a different authenticated transport, which is committed direction and not current. Direct requests carry no principal or actor fields: the broker derives exact context from OS peer UID and trusted configuration, and a unique invocation ID binds an attested claim to its proposal and names the call in audit. Peer mapping distinguishes the gateway UID from the broker UID; it is not process-level attestation. Attested requests add one typed on-behalf-of claim — a canonical external subject and the agent orchestrating for it — which the broker honors only under an owner-configured attestor grant, resolves to a principal through owner-controlled mappings alone, and admits only if policy permits that principal to drive that agent.

The gateway also accepts a public HTTPS path after an external Cloudflare Tunnel/Traefik boundary forwards plain HTTP to its exact WhatsApp callback. That is a wakeup path only: HMAC-authenticated sender and WABA/phone routing facts become an attested proposal scope, while policy, provider credentials, authorization, and effects stay in the broker.

The chart enforces the [current local process boundary](security-model.md#current-local-process-boundary): distinct gateway and broker UIDs, private mounts, and only group-reachable IPC.

A model-facing tool call is only a proposal. The daemon-to-broker request carries that proposal, not trusted identity context or an `AuthorizedInvocation`. The broker owns the authority transition from `ProposedInvocation` to `AuthorizedInvocation`, creating and consuming that state inside the broker-owned execution boundary while evaluating policy, attaching constraints, invoking a provider, and recording evidence. `dekopond` never receives or presents serialized authorization state as a bearer grant, and agent code never receives a raw provider credential. Its complete contract is in [`dekopond.md`](dekopond.md).

## Shared host helpers and privileged provider authority

The SDK's optional host feature carries manifest validation, complete conflict reports, engine construction, and store limits. The broker host's optional compilation cache stores code, never authority. Provider JSON Schemas must be object-shaped, and the host is not a general JSON Schema validator: a provider validates its own operation-specific input.

Model authentication terminates in the model client, separately from provider authority. ChatGPT subscription mode owns a distinct device-flow credential file, refreshes tokens only against OpenAI's fixed authentication host, and sends inference only to the fixed Codex Responses host. It imports no other application's token store and exposes no model credential to a component. Every `dekopon-model` transport — subscription inference, the device-flow exchange, and the OpenAI-compatible client — is built by one agent constructor that disables redirects and ambient proxies, so an exported `HTTPS_PROXY` cannot put a credential-bearing model request on a host nobody named to Dekopon.

The exact fetched standalone JSONPlaceholder v0.1.0 component demonstrates the provider boundary with a read-only GET capability and a distinct external-write POST capability; standalone tests and core loopback integration exercise both without public network access.

`dekopon-broker-host` consumes one non-cloneable `AuthorizedInvocation` at its public execution boundary. An optional destination-bound credential rides alongside that authorization, never inside it, and the native engine injects it strictly after guest-header validation. The legacy selection bindings [will be replaced by public DRNs](design.md#legacy-credential-bindings); broker-owned injection remains. Its rejection tracking is something guest code cannot mask.

Two credential paths reach the broker. Provider credentials resolve from a separate owner-only `credentialsPath` file into per-capability destination-bound values, selectable per acting agent. A separate `secretMapPath` binds public DRNs to physical sources and native sinks; descriptor validation is startup-local, and one selected source lookup follows dual authorization per invocation. Audit records the symbolic name or DRN, never a value or a physical locator. *Committed direction:* the `credential`/`credentialByAgent` bindings will be replaced by public DRNs, preserving per-agent isolation, destination binding, and ChatGPT refresh ([migration requirements](design.md#legacy-credential-bindings)).

Evidence is a redacted public record of a decision and the injection under it. *Committed direction:* removed; the trace is the record ([design.md](design.md#core-concepts)).

Where the broker's audit records go — stdout always, OTLP log records when `telemetry` is configured, and no other copy — is the [`dekopon-brokerd` audit contract](../crates/dekopon-brokerd/README.md#audit).

`dekopon-brokerd provider sync` uses a bounded OCI distribution client to resolve fully qualified exact tag or manifest-digest references and atomically activates a generated lock only after complete host validation. `sync --locked` materializes only locked layer digests; `list`, `verify`, and daemon startup are offline. A managed startup derives immutable blob paths from the lock, and the host compares expected byte length, SHA-256, and provider ID against the same buffer and bounded description it compiles. Publisher provenance, private-registry auth, SemVer selection, pruning, and image-staging integration are absent. The complete authority boundary is in the [`dekopon-brokerd` contract](../crates/dekopon-brokerd/README.md#boundaries), and the provider lifecycle contract under [Managed provider sets](../crates/dekopon-brokerd/README.md#managed-provider-sets).

## Slack Agent continuation boundary

The Agent manifest subscribes to public and private channel message events, but the Slack transport forwards no ambient event. An exact workspace/channel/root-thread/sender claim enters a bounded in-memory LRU only after that message's fresh broker capability surface is non-empty. A later unmentioned message must match all four coordinates, is freshly authorized again, and loses the claim on refusal; another sender and another thread remain ambient. Restart drops every claim.

Only such an inherited message marks its reply optional. The shared prompt loop adds trusted request-scoped guidance plus the payload-free `decline_chat_reply` tool. A decline before capability work yields a typed suppressed completion, stores the sender's text as an unanswered in-memory turn, cleans up activity, and performs no chat delivery or durable recording. If any capability invocation already ran, the loop executes no calls from the decline turn and requires a concise visible report. If no reporting turn remains, the gateway posts a fixed warning that work was attempted and the audit must be checked before retrying. An explicit mention and a direct message never receive the decline tool.

## Storage execution boundary

A storage-enabled operation follows the ordinary authorization transition and additionally consumes one non-cloneable `StorageGrant`. The grant binds the exact component interface and access mode; a wrong-interface call and a denied, quota-exceeded, or over-budget call become sticky even when guest code catches the WIT error. A base-then-generation lease order serializes one scope's authority pointer and invocation access while distinct opaque namespaces overlap freely; grant and begin run as tracked blocking work, so a lease wait cannot stall Tokio workers. Each authorized host write applies directly. A failed response, a trap, and cancellation roll back no completed write. Quota headroom and leases stay held while started native jobs drain; the host makes no invocation-wide atomicity or crash-recovery promise.

The exact standalone memory-chat release is staged under `/opt/dekopon/optional-providers`, outside the default provider scan. The chart mounts its retained provider-storage claim into the broker container alone. The gateway receives no such mount and sends only one typed record proposal after an opaque transport-acceptance receipt.

## Resource evolution

`dekopon.dev/v1alpha1` rejects unknown authored fields to expose typos and ignored authority settings. Transport negotiation is out of scope for the local release. A future daemon API must version resources explicitly and document any field-preservation or compatibility rules before relaxing strict decoding.

The monorepo shares versions, CI, issues, and releases while crate boundaries move together. A crate should move to a separate repository only when ownership or release cadence genuinely diverges.
