## Verification limits and acceptance details

`tool_output(5)` is **not an off-by-one finding**. With exactly the eight scripted requests shown, zero-based request 5 carries the third tool call's result: 0/1 Alice upper, 2/3 Bob upper, 4/5 Alice channel reverse, 6/7 Alice DM reverse. However, the pinned `Fixture` exposes `prompt(index)` at `tests/gateway.rs:552`; no `tool_output` method exists. Add a helper or use the existing extraction pattern, and select the result by tool call identity if prior exchanges can be present. Assert exactly eight requests for this scenario. Explicitly wire the proposed child file with `#[path = "gateway/fauxlack.rs"]` or an equivalent module layout. The helper signature, module declaration and the complete snippet's compilation remain unverified, not confirmed compile defects.

The audit field names in §6 are real: `space.id`, `asker.allowed`, `space.allowed`, `decision.denied_by`, and `conversation.thread` are at `crates/dekopon-broker/src/lib.rs:4837`. Assert the canonical raw `m<n>` value; whether `format!("{:?}", root.id())` produces the required quoted string depends on an API the design has not defined. Do not rely on an opaque/newtype Debug representation.

Define the observation contract for `next_from` before relying on it: a cursor advances once per completed bot answer, progress creation/editing does not count as a final answer, finalization in place becomes observable, and transcript assertions exclude deleted/intermediate progress. Otherwise author equality alone does not identify the intended event. The existing driver supports in-place finalization (`progress/policy.rs:1059`), so a watch bump is not inherently a new reply. A single watch counter can remain the wait mechanism; no extra dispatcher is needed.

There is **no confirmed base race between a completed reply and active steering**: the session seals before final delivery (`session.rs:2824`, `seal_locked` at `:816`). Do not add an idle barrier merely because the admission entry can still exist. Future s2b behavior needs its own implementation/contract review; the kickoff was not supplied beyond the brief's quotations.

The serial transcript assertions do not prove shared model memory, platform recall, reaction behavior, or delivery-coordinate attribution. The scripted final answer `Not here.` does not itself prove denial; the actual `NotGranted` output and DM control make that part non-vacuous. Carol's model-count assertion is meaningful only after observing her terminal unauthorized reply; a zero count immediately after posting could merely mean the event has not been processed.

All proposed fmt, clippy, no-feature/release, all-features tests, rustdoc, dependency-boundary, package, and deny results remain unobserved. The code supports the narrow statements that CI uses all features for tests/lints and no features for daemon/release builds; it does not prove this future feature compiles in either configuration. Documentation gates were also not run under the brief's git/reading-only restriction. No deployed binaries, deployed attestor namespaces, real audit rows, or campaign kickoff files were available to verify release-consumer or post-deploy claims.

## Owner-framing gaps

The single YAML initializes servers, users, channels and DMs, but contains no file definitions. Canvas, snippet and image exist only as Rust constructors, so it does not yet bootstrap all requested object kinds from one manifest. Keep the generic file representation; add a minimal manifest file fixture form if all-object bootstrap is the intended acceptance. No separate canvas service is needed. State explicitly that the proposed canvas is an immutable Markdown attachment, not a shared editable canvas; editable canvas semantics are not exercised by the gateway interface described here.

Multiple servers are represented but never tested. Add one small Rust scenario with the same user/channel IDs in two servers and distinct transport names, checking independent delivery, canonical subjects and resolved spaces. That directly tests the owner's requested isolation without creating a new infrastructure layer. Membership and bot-suppression assertions likewise need an attached receiver and an observed control post; “receives nothing” without proving the receiver is active is vacuous.

The separate broker/gateway fixture configs are appropriate authority inputs and do not violate “one manifest” for chat facts. The in-process seam, existing Rust harness, and no-new-dependency module are proportionate choices. The scope reduction needs honest proof boundaries and a smaller, coherent ship plan, not a more realistic Slack simulator.
