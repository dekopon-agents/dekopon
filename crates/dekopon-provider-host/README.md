# dekopon-provider-host

A bounded, synchronous Wasmtime component host for immediate-mode, read-only Dekopon providers.

Rust providers implement `dekopon_provider_sdk::Provider`; the SDK exports the world mirrored in [`wit/provider.wit`](wit/provider.wit). The host validates each provider manifest and typed response, rejects non-read-only effects, reports every duplicate provider, duplicate capability route, and command-word conflict in one failure rather than stopping at the first, uses one shared engine and runtime mutex to serialize calls, gives every call a fresh Wasmtime store and instance, and enforces memory, table, instance, fuel, wall-clock, input, and output limits. A registry retains compiled components in memory, and `HostOptions::compile_cache_dir` optionally points Wasmtime's content-addressed compilation cache at a directory so a later process reads compiled code back instead of running Cranelift again; without it every process recompiles. Capability schemas must be object-shaped; operation-specific validation remains provider-owned. The linker supplies no WASI or other host imports, so components receive no filesystem, network, clock, environment, or credential authority.

This is the experimental local execution boundary, not the separately deployed authenticated broker path provided by `dekopon-brokerd`. It cannot authorize external effects and deliberately does not accept `AuthorizedInvocation`.

## Command words

A provider whose manifest declares `commandWords` must export one of the two command exports the `dekopon:provider@0.3.0` package declares: `run-command` (`argv` plus an optional piped `stdin`, from the `provider-cli` world) or the legacy `resolve-command` (`argv` alone, from `provider-commands`). The host reads which one the component's type offers at load and refuses a manifest whose words have no callable export (`MissingCommandExport`) or whose export has the wrong type (`CommandExportSignature`); a component built against `0.1.0` or `0.2.0` keeps loading. When both exist, `run-command` is called.

`ProviderRegistry::run_command(word, argv, stdin)` selects the declaring provider by word (`UnknownCommandWord` otherwise, without instantiating anything), bounds `argv` plus `stdin` by `max_input_bytes` before instantiation (`CommandInputTooLarge`), and runs the export through the same empty linker, execution mutex, fresh store, fuel, and wall-clock deadline as `invoke`. The answer is one `CommandRunOutcome` whichever export served it: a capability proposal, rendered text with an exit status, or a decline. A legacy guest never receives `stdin`, by contract. `ProviderRegistry::command_words_by_provider` lists the words each loaded provider declares. The run is a `provider.run_command` span at `DEBUG` carrying the provider, its path, the export name, and byte counts — never the argv or the piped value.

`dekopon-run` calls both: its direct leg snapshots `command_words_by_provider` once per session and runs every command word a script executes through `run_command` inside one non-interruptible `direct-command` process node, so `shell`, `prompt`, and `session replay --provider` all serve provider command words. This crate's tests drive both exports through real components — the checked-in `cli-probe` fixture for `run-command`, including a piped value reaching the guest and each of the three outcomes parsing, and the frozen `provider-v0-2-compat` for the legacy `resolve-command`. No checked-in component exports both, so the rule that `run-command` wins rests on the lookup order in `dekopon-provider-sdk::host::command_export` and its gate tests rather than on an artifact.
